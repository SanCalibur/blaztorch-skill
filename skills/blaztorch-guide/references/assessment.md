# 能力评估与参赛匹配

## 先利用已有对话

优先问具体经历，避免让使用者自己选择“新手/专家”。必要时用三个问题覆盖主要缺口：

1. 最近做成过什么？你亲自负责哪些部分，遇到报错时怎样解决？可以概述，不要求公开代码或上传隐私材料。
2. 这次想学什么、做什么主题？每周可用多少时间，比赛当天是否能集中参与，个人还是已有队友？
3. 线上/线下、语言、预算或设备有什么限制？候选出现特定资格条件后再追问相关身份信息。

用户没有作品时，可邀请其用几句话说明“怎样让一张照片变成表单结果”“模型返回错误数据时会怎么办”。作为可选诊断，不以一次问答划定人的能力上限。

## 六维准备度

由agent根据当前证据形成判断，可直接使用自然语言记录；需要结构化时可使用`level`与`evidence`，未知为`null`。没有固定脚本评估或检验使用者的能力。

| 维度 | 观察证据 |
| --- | --- |
| programming 编程 | 能否改页面、组织数据、定位错误并解释自己的代码 |
| ai AI接入 | 能否调用模型、处理结构化输出、失败和费用限制 |
| data 数据处理 | 能否准备/清洗样本、检查泄漏、理解评价与来源权限 |
| delivery 交付部署 | 能否运行原型、配置密钥、部署或提供稳定演示 |
| product 问题与产品 | 能否说明具体用户、需求证据和项目范围 |
| presentation 展示表达 | 能否演示主要流程并说明改进与局限 |

以下等级仅是agent可参考的粗粒度表达，也可不用数字：

- 0：明确没有尝试过。
- 1：有跟随教程或借助AI完成的经验，仍需要指导。
- 2：能独立完成常见任务，解释关键选择并排查一般问题。
- 3：能处理复杂任务、评估取舍或帮助团队组织相关工作。

自述与可观察例子相互核对；只能看到部分证据时写“初步判断”。不能根据学校、年龄、职业头衔或英文水平推断编程能力。单一总分会掩盖团队角色，不把六维相加后当作参赛资格或获奖概率。

## 当前任务资料示例（虚构）

```json
{
  "skills": {
    "programming": {"level": 1, "evidence": "跟教程改过网页，能解释按钮和表单，复杂错误需要帮助"},
    "ai": {"level": 1, "evidence": "调用过一次模型API，处理过简单JSON"},
    "data": {"level": null, "evidence": "尚未了解"},
    "delivery": {"level": 0, "evidence": "明确说尚未部署过项目"},
    "product": {"level": 2, "evidence": "能描述访谈中的一个具体重复需求"},
    "presentation": {"level": 1, "evidence": "做过课堂展示，未做过限时路演"}
  },
  "interests": ["学习", "智能体"],
  "languages": ["zh", "en"],
  "hours_per_week": 8,
  "team_size": 1,
  "participation": ["online"],
  "registered_event_ids": []
}
```

`team_size`不证明队伍满足人数规则；`languages`是本人可用语言，不是国籍。需要时在会话补充预算、设备、团队分工、所在地及对应公开资格，不必为了模板强行收集。

示例只用于说明agent在会话中如何组织证据，不是脚本输入格式。读取脚本没有能力档案接口。不要将真实能力档案加入本公开仓库。

## 两层判断

### A. 先判断能否进入候选

- 已取消、已结束、作品提交截止：只作历史案例。
- 报名已截止：仅对用户明确已报名的该场赛事讨论继续参赛；尚未报名者排除。
- 时间/时区不明或互相冲突：单列待核对。
- 线下无法到场、身份/地区不符、邀请制或费用超预算：排除并给原因。混合形式不自动等于允许全程远程参赛。
- AI工具禁用、原作不得参赛等规则必须说明；AI技能用于辅导用户不意味着可在比赛中使用AI编码。

### B. 再判断准备度

由agent比较赛题真正要求与六维证据：应用型原型、算法竞赛、训练评估、硬件与行业研究需要不同准备。不能只因标题出现“微调”“硬件”等词，就套用固定等级；需要解释实际任务、工作量、现成工具、可用设备与队友分工。

时间要按本场实际窗口核算：每周8小时不能换算成周末48小时内必定可用8小时；只有日期时不声称还剩准确几小时。工具/数据集能否取得、是否有设备、队友能否覆盖缺口也会改变判断。

用自然语言说明适合尝试或暂不适合的原因。找出最影响交付的1—2个缺口，配一条相关课程或案例；课程能访问不代表全部免费，参照官网的access、accessNotes和limitations。

## 建议结果示例形状

“初步适合应用原型类比赛：你已有表单和API经验，部署是当前主要缺口。这场公开规则允许个人，线上参与；但报名页面的地区条件还需确认。建议你负责界面与主要流程，先补一次部署练习。参赛窗口内能投入的时间请再确认。”

真实输出要补入当次查到的具体赛事与来源，不能把此示例当作某场比赛的事实。不得自动提交报名、测试支付或替用户同意条款。
